# خطة انتقال Pharmacy People إلى استضافة مجانية بالكامل

## القرار التنفيذي

الخيار الأقوى للتطبيق هو **Cloudflare Pages للواجهة + Cloudflare Workers للـ API + Supabase للخدمات المُدارة (Postgres، Auth، Storage)**. يحذف هذا التصميم الخادم الدائم وزمن إيقاظه من مسار الواجهة، ويحافظ على واجهة React/PWA الحالية، ويمنحنا قاعدة بيانات ومصادقة وتخزيناً مُداراً من دون تشغيل خوادم ذاتية.

ليس معنى «مجاني 100%» أنه بلا حدود أو ضمان تعاقدي دائم؛ بل يعني أن خطة التشغيل لا تتطلب بطاقة أو اشتراكاً مادام الاستخدام داخل السقوف المجانية. النطاق الخاص نفسه ليس مجانياً عادةً؛ البديل المجاني هو نطاق فرعي من المزود، أو نقل نطاق تملكه حالياً مع استمرار رسوم تجديده لدى المسجل.

## مقارنة البدائل

| المنصة | مناسبة للتطبيق؟ | نقاط القوة | القيد الحاسم | القرار |
|---|---|---|---|---|
| **Cloudflare + Supabase** | نعم، والأفضل | واجهة CDN سريعة، API قريب من المستخدم، قاعدة PostgreSQL ومصادقة وتخزين في حزمة عملية | Supabase المجاني يتوقف بعد أسبوع من عدم النشاط ولا يقدم نسخاً تلقائية | **المسار الموصى به** |
| **Cloudflare كامل (Pages + Workers + D1 + R2)** | نعم، لكن يحتاج إعادة بناء أكبر | لا خادم دائم، قاعدة D1 مجانية حتى 5GB، قراءة/كتابة ضمن سقوف يومية، وتخزين R2 | نقل MySQL إلى SQLite وإعادة بناء المصادقة وطبقة البيانات؛ أعلى مخاطرة | المسار البديل للسيادة الكاملة على طبقة التطبيق |
| **Netlify + Supabase** | ممكن | نشر Git سهل، وظائف وتخزين مدمجان | 300 رصيد شهرياً؛ قد تتوقف الخدمة عند بلوغ السقف | بديل احتياطي، لا أوصي به أساساً |
| **Vercel Hobby** | لا | تجربة تطوير جيدة | الخطة المجانية للاستخدام الشخصي غير التجاري فقط | مستبعد |
| **GitHub Pages** | لا | مجاني وسريع للملفات الثابتة | لا API آمن ولا قاعدة بيانات ولا تخزين مقيّد بالصلاحيات | مستبعد |

تقدم Cloudflare Workers في الخطة المجانية 100,000 طلب يومياً، والملفات الثابتة غير محدودة الطلبات. وتقدم D1 خمسة ملايين صف مقروء و100,000 صف مكتوب يومياً مع 5GB تخزين، لكن تجاوز الحد اليومي يوقف الاستعلامات حتى التجديد اليومي [1][2]. وتقدم Supabase المجانية 500MB قاعدة بيانات، 1GB تخزين ملفات، 5GB نقل بيانات، و50,000 مستخدم نشط شهرياً، لكنها توقف المشاريع بعد أسبوع من عدم النشاط ولا تشمل النسخ الاحتياطية التلقائية [3].

## البنية المستهدفة

| الطبقة | الاختيار | المبدأ الهندسي |
|---|---|---|
| الواجهة وPWA | Cloudflare Pages | React/Vite الحالي بعد حذف اعتماديات وقت تشغيل المزود الحالي؛ CDN عالمي وملفات ثابتة مخزنة مؤقتاً. |
| API | Cloudflare Workers مع Hono أو tRPC adapter | استبدال Express بطبقة handlers رفيعة؛ لا خادم دائم ولا منافذ ولا أسرار في المتصفح. |
| البيانات | Supabase Postgres | تحويل Drizzle من MySQL إلى PostgreSQL، وترحيلات مصدرة ومراجعة قبل التطبيق. |
| المصادقة | Supabase Auth | Google/بريد إلكتروني، جلسات JWT، وربط الدور والفرع بخوادم وسياسات صفية. |
| الصور والملفات | Supabase Storage | Bucket خاص لإثبات التسليم؛ روابط موقعة قصيرة العمر، ولا BLOB في قاعدة البيانات. |
| الصلاحيات | RLS + فحص API | حماية مزدوجة: سياسات صفية في البيانات، وفحص الدور/الفرع في الـ Worker. |
| النسخ الاحتياطي | تصدير مشفر إلى مخزن خاص مستقل | نسخة قبل كل ترحيل، ونسخة أسبوعية مشفرة إلى مستودع خاص أو مساحة يملكها العميل؛ لا تحفظ بيانات عملاء داخل المستودع العام. |
| المراقبة | قياسات متصفح خفيفة + سجلات Worker + لوحـة صحة | LCP وINP وزمن API ونسبة الفشل؛ تنبيه عند تجاوز حد الاستخدام أو فشل النسخة. |

## مسار انتقال محكوم

### المرحلة 0: تجميد وتعريف النجاح

لا يُلمس الإصدار الحي. تؤخذ نسخة من MySQL، وجرد لمفاتيح التخزين والملفات، وقائمة الأسرار، ومصفوفة أدوار المستخدمين. نحدد بوابة قبول: تطابق عدد السجلات، نجاح صلاحيات كل دور، استرجاع صورة إثبات، ومقارنة زمن أول ظهور قبل/بعد النقل.

### المرحلة 1: بيئة ظل مستقلة

ينشأ مشروعان مجانيان منفصلان للتجربة والإنتاج. يربط Pages بمستودع GitHub، ويُنشأ Worker وSupabase من دون تغيير DNS. تُدار الأسرار داخل إعدادات المزود فقط، ولا توضع في GitHub أو ملفات البيئة المنشورة.

### المرحلة 2: نقل قاعدة البيانات

يُحوّل المخطط من MySQL إلى PostgreSQL؛ لا يُنفذ التحويل مباشرة على الإنتاج. يُستورد dump نظيف بعد تنقية أي سر أو بيانات اختبار غير لازمة. بعد الاستيراد، تنفذ اختبارات العدّ والمفاتيح الأجنبية وعينات محسوبة بالـ checksum قبل السماح بتجربة الواجهة.

### المرحلة 3: المصادقة والصلاحيات والتخزين

يُنقل RBAC إلى جداول Postgres وسياسات RLS، وتُعاد كتابة المصادقة بعيداً عن OAuth الخاص بالمزود الحالي. تُجرّب مسارات المدير والموارد البشرية والمندوب والموظف، ثم تُنقل صور الإثبات إلى Bucket خاص مع تسجيل المفتاح والبيانات الوصفية فقط.

### المرحلة 4: طبقة API والواجهة

تنقل إجراءات tRPC/Express إلى Worker تدريجياً حسب المجال: الموظفون، الحضور، الرواتب، التوصيل، الرسائل. يبقى كل مسار خلف اختبارات contract ثابتة. تُحمّل الخريطة عند الحاجة فقط، وتُفصل استعلامات لوحة التحكم إلى بيانات حرجة ومؤجلة.

### المرحلة 5: الاختبار والأمن والأداء

تنفذ اختبارات الوحدة والصلاحيات، وفحص إدخال الملفات، وتجربة هاتف فعلية، واختبار تحميل خفيف. نضيف budget للحزم وقياسات LCP/INP/CLS. يجب ألا ينقل التطبيق بيانات فرع إلى دور أو مستخدم خارج نطاقه، وتظل الصور الخاصة غير قابلة للوصول بعنوان ثابت.

### المرحلة 6: الإطلاق والرجوع

يُفتح نطاق فرعي تجريبي أولاً، ثم تجربة مستخدمين محدودة. عند قبول النتائج، يُحوّل DNS في نافذة قصيرة مع بقاء الإصدار الحالي سليماً كخطة رجوع. إذا فشل أي معيار قبول، نعيد DNS فوراً، لا نرتجل إصلاحات أثناء الإنتاج.

## تقييم Firebase وAppwrite

### Firebase: قوي تقنياً، لكن ليس خياري الأول لهذه الأداة

Firebase ممتاز عندما تكون الأولوية لتطبيق هاتف أو PWA فوري التحديث: Authentication وFirestore وHosting وCloud Storage متكاملة، والقواعد الأمنية قوية إذا كُتبت واختُبرت بدقة. في خطة Spark بلا تكلفة، يتيح Firestore 1GiB من البيانات و50 ألف قراءة و20 ألف كتابة يومياً، بينما يتيح التخزين 5GB وفق المنطقة ونمط الحاوية [6].

لكن نقل Pharmacy People إليه يعني **إعادة تصميم** لا مجرد نقل استضافة: بياناتنا علائقية ومبنية على MySQL/Drizzle وعلاقات موظف–فرع–رواتب–طلبات–تدقيق. تحويلها إلى Firestore يزيد تعقيد المعاملات والتقارير الأسبوعية وسجل التدقيق. كما أن خدمات Google Cloud المدفوعة مثل Cloud Run وPub/Sub غير متاحة في Spark؛ وربط حساب فوترة ينقل المشروع إلى Blaze [7]. لذا فهو جيد لمنتج جديد قائم على المزامنة الفورية، لكنه ليس المسار الأقل مخاطرة أو الأسرع لتطبيقنا الحالي.

### Appwrite: بديل موحد عملي لكن بسقف أقل من المطلوب

Appwrite يجمع المصادقة والبيانات والتخزين والوظائف في منصة واحدة، وتقدم خطته المجانية 2GB تخزين و5GB نقل و75 ألف مستخدم نشط شهرياً. لكنه يقتصر على قاعدة واحدة وحاوية واحدة ووظيفتين في المشروع، ويوقف المشروع بعد أسبوع من عدم النشاط ولا يقدم نسخاً احتياطية مجانية [8]. يصلح لنموذج أولي أو تطبيق صغير جداً؛ أما بيانات الموارد البشرية وصور الإثبات فتحتاج حذراً أكبر من هذا السقف التشغيلي.

## خلاصة القرار بين Firebase وCloudflare/Supabase

| معيار القرار | Firebase Spark | Cloudflare + Supabase |
|---|---|---|
| ملاءمة نموذج البيانات الحالي | منخفضة؛ انتقال إلى NoSQL وإعادة تصميم كبيرة | مرتفعة؛ PostgreSQL قريب من النموذج العلاقي الحالي |
| سرعة تنفيذ النقل | متوسطة إلى بطيئة | متوسطة؛ تغيير API وقاعدة البيانات فقط |
| أداء الواجهة | ممتاز مع Hosting | ممتاز مع Pages وCDN |
| تحديثات لحظية | ممتازة | متاحة عبر Supabase Realtime عند الحاجة |
| احتمال القفز إلى خطة مدفوعة | مرتفع عند الحاجة لخدمات Google Cloud الخلفية | أقل في البداية؛ تُراقَب سقوف Supabase وCloudflare |
| التوصية للأداة الحالية | بديل مقبول، لا أوصي به كمسار أول | **المسار الأول الموصى به** |

## ما لا أعد به

لا يوجد مزود يضمن «مجاني دائماً بلا حدود» لتطبيق أعمال يتوسع أو يخزن صوراً وبيانات موارد بشرية. كذلك لا أوصي بتجاوز شروط الاستخدام؛ فخطة Vercel Hobby محصورة بالاستخدام الشخصي غير التجاري [4]. الخطة الصحيحة تجعل الخدمة مجانية ضمن حدود معلنة، وتراقب السقوف مبكراً، وتحافظ على قابلية ترقية منظمة إن زاد الاستخدام.

## القراران المطلوبان قبل التنفيذ

1. اعتماد **Cloudflare + Supabase** كمسار أولي، أو اختيار Cloudflare كامل مع قبول زيادة مدة إعادة البناء.
2. تحديد وسيلة حفظ النسخ المشفرة: مستودع GitHub خاص مخصص للنسخ، أو مساحة تخزين يملكها العميل. لا أضع قواعد البيانات أو صور العملاء في المستودع العام.
